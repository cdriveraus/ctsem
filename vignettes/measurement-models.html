A ctsem model has two halves. The dynamic half says how the latent processes evolve between observations; the measurement half says how an observation at a time point relates to the latent state then. This vignette is entirely about the second half: how many indicators load on a process, what kind of variable each indicator is, what happens when kinds are mixed, and what to do when a loading or a residual is not a constant.

Everything here uses backend = 'julia'. The non-Gaussian indicator types (ordinal, count, censored) exist only on that backend, and binary is integrated there rather than linearised, so a vignette that switched backends between sections would not be comparing like with like.

The measurement equation

At each observed time point the filter has a predicted latent state η\eta. For every manifest variable jj observed at that row, ctsem forms a linear predictor

μj=MANIFESTMEANSj+LAMBDAj⋅η \mu_j \;=\; \text{MANIFESTMEANS}_j \;+\; \text{LAMBDA}_{j\cdot}\, \eta

and then attaches an observation model to it, chosen by that variable’s manifesttype:

manifesttype Variable Observation model Residual
0 continuous yj∼N(μj,MANIFESTVAR)y_j \sim N(\mu_j,\ \text{MANIFESTVAR}) free
1 binary, coded 0/1 P(yj=1)=logit−1(μj)P(y_j = 1) = \text{logit}^{-1}(\mu_j) none
2 ordinal, coded 1..K1..K P(yj≤k)=logit−1(τjk−μj)P(y_j \le k) = \text{logit}^{-1}(\tau_{jk} - \mu_j) none
3 count, non-negative integers yj∼Poisson(eμj+ej)y_j \sim \text{Poisson}(e^{\mu_j + e_j}), ej∼N(0,MANIFESTVAR)e_j \sim N(0, \text{MANIFESTVAR}) free
4 censored N(μj,MANIFESTVAR)N(\mu_j,\ \text{MANIFESTVAR}), observed only inside [cj−,cj+][\,c^-_j, c^+_j\,] free

Four things follow from that table and are worth stating before any code.

Binary and ordinal indicators have no residual variance. Their randomness is entirely in the link, and a term added to the linear predictor would not be identified if you wanted one: under a probit link EeΦ(μj+e)=Φ(μj/1+v)E_e\,\Phi(\mu_j + e) = \Phi(\mu_j / \sqrt{1 + v}) exactly, so such a term is absorbed into the loadings and thresholds, and the logistic link differs only in that the absorption is approximate. Their rows and columns of MANIFESTVAR are fixed to zero, and ctFit() fixes any that were left free.

The other three do have one, and it means something different in each. For a continuous indicator it is the usual measurement error variance. For a censored one it is the variance of the Gaussian that is observed only inside the limits. For a count it is a dispersion: a Gaussian term added to the log rate, making the observation Poisson-lognormal rather than Poisson. It is identified where the binary and ordinal versions of it are not, because a Poisson’s variance is locked to its mean — the dispersion shifts the mean by v/2v/2, which MANIFESTMEANS absorbs, and multiplies the variance by a factor nothing else in the model can produce. It is the only parameter in a ctsem model that moves a count’s variance-to-mean ratio, and leaving it out does not make the data equidispersed: it makes DIFFUSION absorb the difference, which is usually the parameter the model was for. Only the diagonal counts — a count row is scored on its own, so it has no correlated measurement error, and ctFit() fixes a free off-diagonal to zero.

The scale of the latent process has to come from somewhere. With a Gaussian indicator you can anchor it by fixing a loading, or by fixing DIFFUSION. With only binary or ordinal indicators there is no free residual to trade against, so a loading and the process scale are two names for one quantity: fix the loadings and let DIFFUSION carry the scale.

Location works the same way. CINT and T0MEANS set where the process sits, and each indicator’s MANIFESTMEANS sets where that indicator sits relative to it. ctsem’s default fixes CINT and T0MEANS to zero and frees MANIFESTMEANS, which is what the examples below use — ordinal indicators included. An ordinal indicator’s thresholds are also locations, so one among them is redundant: adding a constant to μj\mu_j and to every τjk\tau_{jk} leaves the cumulative logit unchanged. ctsem resolves that by pinning τj1\tau_{j1} at zero, so the location of an ordinal indicator lives in its MANIFESTMEANS like everyone else’s, and what THRESHOLDS estimates is the K-2 gaps between successive thresholds. The point of putting it there rather than in τj1\tau_{j1} is that MANIFESTMEANS can be indvarying: one random effect then shifts all of an indicator’s category boundaries together, which is what “this person answers higher” means, where a random effect on the thresholds would need one per boundary.

A single indicator

With one indicator per process the loading is not estimable and is fixed, by convention to 1. That does not mean measurement error is inestimable: in a continuous time model the measurement error and the process innovation have different signatures across the time interval, so MANIFESTVAR and DIFFUSION remain separately identified.

msingle <- ctModel(type = 'ct', n.latent = 1, n.manifest = 1,
  manifestNames = 'y1', latentNames = 'eta1', LAMBDA = matrix(1),
  CINT = matrix(0), T0MEANS = matrix(0))
msingle$pars$indvarying <- FALSE

Anchoring, and where the optimiser starts

Fixing LAMBDA[1,1] is not the only way to set the scale — fixing DIFFUSION to 1 and freeing all three loadings fits the same model, and reports loadings on the process’s own scale instead of on y1’s.

The two are equivalent in principle but not always in practice, because where the optimiser starts matters. ctFit reads the starting values for the variance diagonals off the data by default, through optimcontrol$datastart. Before that it began every fit from a fixed point that put DIFFUSION near 7 whatever the data were measured in, and on data at a much smaller scale a loading-anchored model would collapse the latent to zero variance and explain the whole signal as measurement error — a local optimum, with the loadings running off to implausible magnitudes to compensate. On the data above rescaled by 1/100 that failed on four starting seeds out of four, and converges on four out of four now.

It is not a guarantee. A model can sit near a basin boundary at a given scale, where the small random jitter ctsem still adds to the start is enough to decide which optimum the fit reaches — on the same data rescaled by 100, two seeds in four land 328 log units apart, with or without the derived start. So a fit reporting non-convergence, or loadings nowhere near anything plausible, is worth re-running, and worth checking against DIFFUSION-anchored scaling or explicit inits.

The five indicator types

To see each type on its own, generate one latent trajectory and then measure it five different ways. Generating the process with a near-zero measurement variance makes the single manifest variable a direct readout of the latent state, which the indicators below are built from:

set.seed(5)
nsub <- 80; nobs <- 10
process <- ctModel(type = 'ct', n.latent = 1, n.manifest = 1,
  manifestNames = 'eta', latentNames = 'eta1', LAMBDA = matrix(1),
  DRIFT = matrix(-0.4), DIFFUSION = matrix(1), T0VAR = matrix(1.12),
  T0MEANS = matrix(0), CINT = matrix(0), MANIFESTMEANS = matrix(0),
  MANIFESTVAR = matrix(1e-6), Tpoints = nobs)

d <- data.frame(ctGenerate(process, n.subjects = nsub, Tpoints = nobs,
  backend = 'r'))
eta <- d$eta

Two indicators of each kind, built by applying each row of the table above by hand, so that the link in the model and the link in the simulation are visibly the same thing:

invlogit <- function(x) 1 / (1 + exp(-x))
ordinaldraw <- function(mu, tau) {          # cumulative logit
  cum <- sapply(tau, function(k) invlogit(k - mu))
  p <- cbind(cum, 1)
  p <- cbind(p[, 1, drop = FALSE], t(apply(p, 1, diff)))
  apply(p, 1, function(pr) sample.int(length(pr), 1, prob = pmax(pr, 0)))
}
tau <- c(-1, 0, 1)                          # four categories

d$y1 <- 0.0 + eta + rnorm(nrow(d), 0, 0.6)              # 0 continuous
d$y2 <- 0.5 + eta + rnorm(nrow(d), 0, 0.6)
d$b1 <- rbinom(nrow(d), 1, invlogit(-0.4 + eta))        # 1 binary
d$b2 <- rbinom(nrow(d), 1, invlogit( 0.4 + eta))
d$o1 <- ordinaldraw(eta, tau)                           # 2 ordinal
d$o2 <- ordinaldraw(eta, tau)
disp <- 0.3                                 # count dispersion, on the log rate
d$c1 <- rpois(nrow(d),                                  # 3 count
  exp(1.4 + 0.5 * eta + rnorm(nrow(d), 0, disp)))
d$c2 <- rpois(nrow(d), exp(1.2 + 0.5 * eta + rnorm(nrow(d), 0, disp)))
d$x1 <- pmin(pmax(2.0 + eta + rnorm(nrow(d), 0, 0.5), 0), 4)   # 4 censored
d$x2 <- pmin(pmax(1.8 + eta + rnorm(nrow(d), 0, 0.5), 0), 4)

d$eta <- NULL

Specifying each type

manifesttype is a vector with one entry per manifest variable. Two of the types need something extra alongside it, and both are needed because ctModel() never sees the data:

  • ordinal needs ncategories, so that the right number of thresholds can be created. ctGenerate() needs it for the same reason.
  • censored needs censormin and censormax. These are known constants rather than parameters: an instrument’s floor and ceiling are properties of the instrument, and the data cannot inform them. A variable censored on one side only leaves the other infinite.

A helper, since the five models below differ only in which columns they take:

buildmodel <- function(names, type, lambda = 1, ncat = 0,
  cmin = -Inf, cmax = Inf) {
  n <- length(names)
  # binary and ordinal are the two types with no residual of any kind
  mvar <- diag(0, n)
  if (type %in% c(0, 3, 4)) diag(mvar) <- paste0('mvar_', names)
  m <- ctModel(type = 'ct', n.latent = 1, n.manifest = n,
    manifestNames = names, latentNames = 'eta1',
    manifesttype = rep(type, n), ncategories = rep(ncat, n),
    censormin = rep(cmin, n), censormax = rep(cmax, n),
    LAMBDA = matrix(lambda, n, 1),
    MANIFESTMEANS = matrix(paste0('mm_', names), n, 1), MANIFESTVAR = mvar,
    CINT = matrix(0), T0MEANS = matrix(0))
  m$pars$indvarying <- FALSE
  m
}

models <- list(
  continuous = buildmodel(c('y1', 'y2'), 0),
  binary     = buildmodel(c('b1', 'b2'), 1),
  ordinal    = buildmodel(c('o1', 'o2'), 2, ncat = 4),
  count      = buildmodel(c('c1', 'c2'), 3, lambda = 0.5),
  censored   = buildmodel(c('x1', 'x2'), 4, cmin = 0, cmax = 4))

Every one of these fixes its loadings rather than freeing them, so that the latent scale is anchored the same way in all five and the dynamic estimates below can be read side by side.

The count pair is fixed at 0.5 rather than 1, and that is a choice worth making deliberately. A count’s loading sets how far its log rate travels as the process moves, and the exponential turns a wide latent range into a very skewed observation. The filter carries a Gaussian summary of the state, and a Poisson update is well summarised that way only while the rate stays in a moderate range. Measured on this design at 200 subjects and 12 occasions: a count read directly off a process with a standard deviation of 1.12 – log rates spanning about seven units, rates from 0.05 to 50 – recovers DRIFT at -0.20 and -0.32 on two seeds against a generating -0.4, and DIFFUSION at 0.69 and 0.74 against 1. The same process at a standard deviation of 0.45 recovers -0.407 and -0.418, and its DIFFUSION to within 0.012. Halving the loading halves the range the link sees, which is why the count column below is as accurate as the others. If your counts genuinely do swing over orders of magnitude, treat the dynamic estimates from them with the same suspicion.

The count models here also estimate a MANIFESTVAR diagonal, which for a count is the dispersion rather than a measurement error: a Gaussian term on the log rate, so the observation is Poisson-lognormal. The counts above were generated with one, of 0.3. Freeing it is worth doing on real counts whatever you expect, because the alternative is not a Poisson assumption quietly satisfied — it is DIFFUSION absorbing whatever overdispersion there is, and DIFFUSION is usually the parameter the model was for.

Every row of that table estimates the same two generating values, −0.4-0.4 and 11, from the same latent trajectory, and every row is within about one standard error of them. What differs is how much of the trajectory each instrument transmits, which is visible in the standard errors rather than in the estimates: two binary items per occasion carry a few bits about a continuous state and are the least precise by a factor of two, while the continuous, censored and count pairs each recover DRIFT to about 0.05.

The parameters specific to a type appear in the same summary. An ordinal indicator’s location is in MANIFESTMEANS; THRESHOLDS holds the first threshold, pinned at zero and not reported, and then the gap to each subsequent one, which is what keeps them ordered. So a four category variable contributes one mean and two gaps:

Combining types

Several types on one latent

Nothing stops indicators of different types from loading on the same process. Each contributes its own likelihood term against the same predicted state, and the filter’s update at that row takes all of them:

mixednames <- c('y1', 'b1', 'o1', 'c1', 'x1')
mvar <- diag(0, 5)
mvar[1, 1] <- 'mvar_y1'      # measurement error
mvar[4, 4] <- 'mvar_c1'      # the count's dispersion
mvar[5, 5] <- 'mvar_x1'      # the scale inside the censoring limits

mmixed <- ctModel(type = 'ct', n.latent = 1, n.manifest = 5,
  manifestNames = mixednames, latentNames = 'eta1',
  manifesttype = c(0, 1, 2, 3, 4),
  ncategories   = c(0, 0, 4, 0, 0),
  censormin     = c(-Inf, -Inf, -Inf, -Inf, 0),
  censormax     = c( Inf,  Inf,  Inf,  Inf, 4),
  LAMBDA = matrix(c(1, 1, 1, 0.5, 1), 5, 1),   # the count as generated
  MANIFESTMEANS = matrix(paste0('mm_', mixednames), 5, 1),
  MANIFESTVAR = mvar, CINT = matrix(0), T0MEANS = matrix(0))
mmixed$pars$indvarying <- FALSE

One indicator of each kind recovers the process about as precisely as the best same-kind pair above, and roughly twice as precisely as the binary or ordinal pairs – with the thresholds, the three MANIFESTVAR entries and five intercepts all estimated alongside. That is the practical argument for using indicators of every kind you have, rather than keeping only whichever are convenient to model.

Several types on different latents

More usually the types are not interchangeable measures of one thing. An ordinal questionnaire item and a binary event indicator measure one construct; a count, a censored scale score and a plain continuous variable measure another; and the question is how the two constructs drive each other. That is a two-process model with a block-structured LAMBDA.

set.seed(11)
twonames <- c('o1', 'b1', 'c1', 'x1', 'y1')
lambda2 <- matrix(0, 5, 2)
lambda2[1:2, 1] <- 1     # ordinal and binary measure eta1
lambda2[3:5, 2] <- 1     # count, censored and continuous measure eta2

genvar <- diag(0, 5)
genvar[3, 3] <- 0.3      # the count's dispersion, on its log rate
genvar[4, 4] <- 0.4
genvar[5, 5] <- 0.6
gen2 <- ctModel(type = 'ct', n.latent = 2, n.manifest = 5,
  manifestNames = twonames, latentNames = c('eta1', 'eta2'),
  manifesttype = c(2, 1, 3, 4, 0), ncategories = c(4, 0, 0, 0, 0),
  censormin = c(-Inf, -Inf, -Inf, 0, -Inf),
  censormax = c(Inf, Inf, Inf, 4, Inf),
  LAMBDA = lambda2,
  DRIFT = matrix(c(-0.4, 0.25, -0.15, -0.7), 2, 2, byrow = TRUE),
  DIFFUSION = diag(0.8, 2), T0VAR = diag(1, 2), T0MEANS = matrix(0, 2, 1),
  CINT = matrix(0, 2, 1),
  MANIFESTMEANS = matrix(c(1, -0.4, 0.5, 2.0, 0.3), 5, 1),
  MANIFESTVAR = genvar, Tpoints = 10)

# The first threshold is pinned at zero and the rest are gaps, so thresholds of

gen2$pars$value[gen2$pars$matrix %in% 'THRESHOLDS' & gen2$pars$col > 1] <- 1

ctGenerate(backend = 'julia') draws each row from its own prior predictive as the filter reaches it, so it applies the links above rather than producing continuous values for a variable the model calls binary. The R generator integrates a linear Gaussian system and has no notion of a link; it warns if asked to generate from a model with non-Gaussian indicators.

The estimation model has the same block structure, with the measurement parameters freed:

estvar <- diag(0, 5)
estvar[3, 3] <- 'mvar_c1'
estvar[4, 4] <- 'mvar_x1'
estvar[5, 5] <- 'mvar_y1'

  manifestNames = twonames, latentNames = c('eta1', 'eta2'),

State-dependent measurement

A LAMBDA or MANIFESTVAR cell need not be a constant. Writing a latent process name into the cell makes it an expression evaluated at the current state, so an instrument can become more or less sensitive, or noisier, as the process moves.

Free parameters used inside such an expression have to live in the PARS matrix: a cell containing an expression is the specification itself rather than a labelled parameter, so ctsem resolves names appearing in it against PARS. PARS entries are identity-transformed and unbounded, which is why the residual below is written as exp(...) — that is what keeps a standard deviation positive.

Data where the second indicator’s loading rises with the process, and the first indicator’s residual standard deviation rises with it too:

ctModelIsNonlinear() reports that such a model has cells with no single value, so every summary of it is a reading at one particular state:

ctModelIsNonlinear(fsd)
#> [1] TRUE

Which is why the honest picture of a state-dependent model is a curve rather than a number. ctStateDependencePlot() finds the cells that actually move — by materialising every model matrix across a grid of states and keeping the ones whose value changes, so dependence arriving indirectly, through a PARS entry or through a covariance built from a dependent cell, is caught too — and draws each of them against the process:

ctStateDependencePlot(fsd, along = 'eta1', nsamples = 30)

One panel is the loading on y2, rising with eta1. The other is the residual variance of y1 — MANIFESTcov rather than MANIFESTVAR, since that is the covariance the filter actually uses — rising with it as well. A summary() of this model reports one point from each of those curves.

Only LAMBDA and MANIFESTVAR are state-dependent here, but the same mechanism applies to MANIFESTMEANS, and on the dynamic side to DRIFT, DIFFUSION and CINT.

Summary

  • manifesttype picks the observation model per indicator: 0 continuous, 1 binary, 2 ordinal (with ncategories), 3 count, 4 censored (with censormin and censormax). Everything but 0 needs backend = 'julia'.
  • Continuous, count and censored indicators each have a free MANIFESTVAR diagonal, meaning a measurement error variance, a log-scale dispersion, and the variance inside the limits respectively. Binary and ordinal have none; fix theirs to zero.
  • An ordinal indicator’s location is its MANIFESTMEANS, like every other indicator’s. THRESHOLDS pins the first threshold at zero and estimates the K-2 gaps, so a person-level shift of the whole category scale is one random effect on the mean rather than one per boundary.
  • Anchor the latent scale exactly once: a fixed loading, or a fixed DIFFUSION. With no Gaussian indicator on a process it has to be the loadings.
  • A count indicator’s loading sets how far its log rate travels. Keep that range moderate – the filter’s Gaussian summary of a Poisson update degrades once the rate swings over orders of magnitude, and the dynamic parameters come back attenuated.
  • Types can be mixed freely, on one process or across several.
  • A LAMBDA or MANIFESTVAR cell written as an expression in a latent process name is evaluated at the current state; free parameters inside it go in PARS, and ctStateDependencePlot() shows what the result claims.
